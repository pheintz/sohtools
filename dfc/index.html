Damage Flag Corruption

Hit something with a weapon that is its own actor, freeze the target before it processes the hit, let the weapon actor die, and put something new in the memory it used. When the target thaws, its hit record still points into the dead weapon, and it acts on whatever bytes are there now.

Companion to the Bottle Setup Matrix (heap words per setup) Offsets are retail N64 (SoH headers are 0x10 larger past 0x13C) Updated Oct 13 2026

What the code changes in the current notes

Most of the community explanation holds up. These are the places where the code says something more specific or different.

One hit, frame by frame

  1. Frame k−1
    The boulder's update registers its hurtbox (only while Link is within 800 units). The seed's draw registers a hitbox swept from last frame's tip to this frame's tip.
  2. Frame k, start
    The collision pass runs before any actor updates. Seed bit 0x00000004 is in the boulder mask 0x4FC1FFFE, so the hit lands: the boulder gets AC_HIT and a pointer to the seed's damage record (seed + 0x198), and the seed gets AT_HIT. The damage table math also runs here.
  3. Frame k, Link
    Actors update in category order: switch, BG, player, explosive, NPC, enemy, prop, item action, misc, boss, door, chest. The freeze test for each category reads Link's flags at the moment that category comes up. The bottle takes effect in Link's update and sets state flags 28 and 29.
  4. Frame k, boulder
    Props freeze on DEAD | 28, so the boulder skips its update. It doesn't read the hit, and it doesn't re-register its hurtbox, which is what would clear the hit flag and the pointer. The frozen branch also zeroes its damage number.
  5. Frame k, seed
    Item actions never freeze by category, but EnArrow_Update refuses to run during a blocking cutscene unless Link fired something in the last 4 frames (unk_A73). Inside that window the seed runs, sees its own hit, plays the clank and kills itself.
  6. Frame k+1
    The dead seed is deleted and its 0x280 byte heap block (0x250 instance + 0x30 header) is free.
  7. During the cutscene
    The bottle releases its contents. On N64 the item's overlay code is allocated first, first fit, so it lands on the seed's old block. Seed + 0x198 now holds a MIPS instruction; for fish it is E426xxxx, a swc1 whose low half is a relocated address.
  8. Thaw frame
    The collision pass runs first, but the boulder isn't in the hurtbox list, so nothing overwrites its record. Then its update reads AC_HIT, follows the stale pointer, finds bit 30 (hammer jump) in E426xxxx, and breaks.
Necessary conditions

What a target needs

1. Its hurtbox accepts the starting weapon

The collision pass only registers a hit if the weapon's flags share a bit with the target's hurtbox mask. The swap happens after that test, so it can't create a hit the mask would refuse.

seed 0x4 · arrow 0x20 · fire/ice/light arrow 0x800/0x1000/0x2000 · magic spin 0x400000 / 0x800000 / 0x1000000 (Kokiri / Biggoron / Master) · charged past 85% uses jump bits 0x2000000 / 0x4000000 / 0x8000000

2. Its own update reads the attacker's data

The target must look through the stored pointer later: the attacker's flags (acHitElem->atDmgInfo.dmgFlags), its damage byte, or the attacker actor itself (ac->id, position, facing). Targets that act on AC_HIT alone, or only on the table damage, get nothing from the swap.

3. It is frozen on the frame the hit is detected

Bottles set state 28, which freezes switch, BG, explosive, enemy, prop, misc, boss and chest actors. NPC, item action, door and player actors never freeze for a bottle. Categories that update after Link need the bottle on the hit frame; switch and BG need it one frame earlier.

4. Its hurtbox is on when the weapon arrives

Some targets only register a hurtbox near Link. Boulders: 800 units (xz). Bronze boulders, small rocks, pots: 600. Torches and beehives: always. Flobbery muscle blocks: only while raised.

On the weapon side, the weapon actor has to die during the freeze, and the new allocation has to cover its damage word: seed or arrow + 0x198, spin + 0x154.

An arrow that touches an actor on F2 to F11 starts its 50 frame bounce instead, then hangs frozen and never dies. Only the hit that is found on F12 meets the timer first. The second shot can be on F9, F10 or F11 (leaving 1 to 3 on F12); F8 is too early. Gravity starts on F5 and has dropped the arrow about 17 units by F11. The path figures run from the release point; the hitbox tip sits about 15 units ahead of the arrow, and the target's own radius widens the window.

The missing piece for torches is memory. The second arrow survives the cutscene, frozen in the air, and keeps its block. Arrow 1 frees 0x280 bytes plus two 0x50 SkelAnime blocks. If arrow 2 (or anything else alive) starts right after them, the hole is only 0x320 bytes. Fish code needs 0x2110 contiguous bytes and bug code 0x2520, so neither can land. The fish instance fits instead, and fish + 0x198 is a collider limb byte: 00000000, no fire bit, no light. For a fire bit (fish E426xxxx has bit 17, bugs 00808825 have bit 11) nothing alive may start within that many bytes after arrow 1. Compare the two arrow addresses on a failed and a working attempt.

What lands in the hole

When the bottle item spawns, its overlay code is allocated first, then its instance. Both take the first free block that is big enough. If the item's code is already loaded (another one of it is alive, or it's the fairy, whose code Navi keeps loaded), only the instance is allocated, and the stale word becomes a field of the new actor.

Check of the Ganondorf setup

Bomb at A, seed at A + 0x230, bomb gone, bugs released: bug 1 at A, bug 2 at A + 0x350. Bug 2 + 0x78 is its floorPoly pointer, which sits exactly on seed + 0x198. The sizes match N64 (bomb 0x200 data + 0x30 header, bug 0x320 + 0x30). Bug 2 − seed = bug block − bomb block = 0x120 whatever the header size, so the same layout also lines up on GameCube. Ganondorf only needs bit 13 (0x2000) of that pointer, so it depends on which floor triangle bug 2 lands on. On NTSC 1.0, look for a bug at seed + 0x120 (bug 1 will be at seed − 0x230).

Ship of Harkinian has no overlays and uses the system allocator, so stale words there are not reproducible.

Not settled

Open items

  • AFBF0014 after Song of Storms. It is sw ra, 0x14(sp), a function prologue. Neither Storms actor explains it at the plain offset: Oceff_Storm's code never lands in holes, and En_Okarina_Effect has 02002025 at +0x198 (this word is at its +0x18, +0x84, +0xCC and +0x328). If that code is the source, it started 0x190 bytes before the seed, meaning the block in front of the seed was free too. The seed's address and the effect's address would settle it.
  • 0C0131DC is jal 0x8004C770, a call into the main code segment, so its value depends on the game version. It isn't in any NTSC 1.0 or GameCube PAL actor overlay.
  • The video's cancel-aim recipe. Cancelling the aim within 4 frames of a shot launches the nocked arrow instead of deleting it. After that window, cancelling deletes the nocked arrow and frees its block, which can merge holes. That may be what made the video's layout work.
  • Saria's Song in the forest. Story flags that change which actors a scene spawns change the heap, so the same setup can read a different word. The exact actors weren't checked.
