# rba-data — OoT Bingo v10.6 × Reverse Bottle Adventure

A data pipeline that joins every OoT Bingo **v10.6** goal to:

- **how to complete it with Reverse Bottle Adventure** — exact C-Right item, bottle modifier, setup;
- **the RBA traps** — what each write destroys, and what can never be written back;
- **the intended (non-glitched) route** and its quest prerequisites.

Everything mechanical is derived from the OoT decompilation and cross-checked against
ZeldaSpeedRuns; every hand-written claim carries a provenance note. Nothing here is guessed silently
— where a fact could not be established it is listed in `out/open-questions.md`.

## Run it

```bash
node build_all.js
```

Twenty scripts, no dependencies. It produces two pages and a machine-readable dataset.
Eleven steps assert rather than just emit:

- `rba_recipes.js` fails loudly if a recipe references a goal name that is not **exactly** a v10.6
  goal name. It used to strip an inline `" — explanation"` suffix before comparing, which let a
  `"Goal name — why"` entry pass while every consumer matched on the raw string and silently
  dropped it; that cost three goals their RBA links. Prose now belongs in the `*Notes` maps, and a
  `*Notes` key with no matching list entry is also an error.
- `prerequisites.js` fails if a spawn-window key is not a v10.6 goal name.
- `collections.js` fails if the gold-skulltula area groupings stop reproducing the counts stated in
  the goal names, and fails *before* writing `collections.json` rather than after.
- `validate_community.js` fails if the community location lists contradict bingo's own synergy
  categories, the goal counts, or `collections.js`.
- `tkc_tips.js` fails if any heading in the strategy source matches no v10.6 goal, so a renamed goal
  cannot silently drop its notes.
- `validate_claims.js` fails if any recipe claims to *satisfy* a goal RBA cannot actually reach.
  It runs **before** `build_merged.js`, so an overclaim aborts the run instead of being baked into
  a dataset that then looks authoritative.
- `validate_rules.js` checks claims against ootbingo's **official goal clarifications**, read back
  out of the bingo repo so an edited rule fails the build instead of being validated against a
  stale copy. Mechanical reachability is necessary and not sufficient — a race is judged on the
  rules, not the memory map.
- `build_merged.js` refuses to write a dataset when a check is failing — it exits, rather than
  setting an exit code and writing anyway.
- `build_board_data.js` fails if a board generated from the trimmed goal lists differs by even one
  square from the same board generated by the untouched bingo pipeline.
- `verify_board_synergy.js` fails if the SynergyCalculator port drifts from the generator, and
  separately drives the page's **own** `parseBoardInput` against real `bingo.html` URLs. The seed
  reaches the generator as a string, exactly as ootbingo passes it: seedrandom keys on
  `seed.toString()`, so `?seed=007` and `?seed=7` are different boards. Coercing with `Number()`
  produced a different 25 squares under a heading reading "Board 007", and 1,600 board-parity
  comparisons never noticed because they never went through the parse.
- `build_goals_page.js` and `build_rba_page.js` fail if any colour pair drops below WCAG AA in
  **any** theme, or if a form control loses its accessible name (see `a11y.js`). "Any" is three:
  light, `[data-theme="dark"]`, and the `@media (prefers-color-scheme: dark)` block — which is the
  one most readers actually get and which went unchecked for a long time. The two dark blocks are
  hand-duplicated, so the gate now also fails if they drift apart. Pairs come from a hand list *plus*
  every self-contained pairing found in the CSS, so a new `color:`/`background:` rule is checked
  without anyone remembering to add it.

## What RBA can never grant

Derived from the writable set `{20, 24, 25, 28, 29, 31}` and checked on every build:

| bit | status | why |
|---|---|---|
| 0, 2, 3, 4 | settable | set directly by one of 20/24/25/28/29 |
| **1** | **unreachable** | only 31 sets it, and 31 needs the byte to already read 26 = `0b00011010`, which *already has bit 1* — circular |
| **5, 6, 7** | **unreachable** | no writable value contains them |

Because a write assigns the whole byte, the post-state is exactly the value written. So anything in
bits 1, 5, 6 or 7 is state RBA can **destroy but never grant**:

| byte | bit 1 | bits 5-7 |
|---|---|---|
| swords / shields | Master Sword | Hylian Shield, Mirror Shield |
| tunics / boots | Goron Tunic | Iron Boots, Hover Boots |
| spiritual stones | Song of Storms | Stone of Agony, Gerudo's Card, GS icon |
| songs | Requiem of Spirit | Epona's Song, Saria's Song, Sun's Song |
| medallions | Fire Medallion | Light Medallion, Minuet, Bolero |
| dungeon items | **Compass** | — |

## Songs span three bytes

Song goals are not decided by one write. Song of Time and Song of Storms live in the **stones** byte
(Odd Potion, stop 5); Serenade, Requiem, Nocturne, Prelude, Lullaby, Epona, Saria and Sun live in the
**songs** byte (Poacher's Saw, stop 6); Minuet and Bolero live in the **medallions** byte
(Broken Goron's Sword, stop 7). Odd Potion and Poacher's Saw are consecutive trade stops, so both
writes fit in one run.

Applying the bit rule across all three, RBA can newly grant exactly **five** songs — Song of Time,
Serenade, Nocturne, Prelude and Zelda's Lullaby. Song of Storms, Requiem, Epona, Saria, Sun, Minuet
and Bolero all sit in bit 1 or bits 5-7 and can only be destroyed.

That puts a hard ceiling of **seven** songs (the five, plus Minuet and Bolero if the medallions byte
is never written) before you have to go and re-learn anything. Recorded as a `COMBINATIONS` entry in
`rba_recipes.js` with the per-goal consequences.

This is what made the dungeon Compass a closed loop, and it is not specific to dungeon items. The
validator caught four claims that had it backwards — *Goron Tunic*, *Requiem of Spirit*,
*Fire Medallion* and *2 Shields* were all listed as things RBA could complete.

## Whole boards, and ranking the twelve lines

Paste a board link and the page rebuilds the exact board, then ranks every line you could win on:

```
goals-page.html?version=10.5.1&seed=523297&mode=normal
```

A bare seed works too, as does the row popout link below. A board is a pure function of
(version, seed, mode), so the page carries **ootbingo's own `generator.js`** rather than a
reimplementation — a seeded RNG walk over a weighted shuffle is exactly the kind of thing a
faithful-looking port gets subtly wrong, producing a plausible board that is silently not the one
being raced. `build_board_data.js` regenerates 1600+ boards from the untouched pipeline and from
the trimmed payload the page ships, across both modes and both versions, and fails the build if a
single square differs.

Versions **10.6** and **10.5.1** are embedded (`BOARD_VERSIONS` in `build_board_data.js`; adding one
is a one-line change). They share 252 goals, so a 10.5.1 board is almost fully annotated by a
v10.6 dataset; anything unmatched is named rather than silently dropped.

### The synergy number is the generator's own

Each of the 12 lines is scored with ootbingo's `SynergyCalculator`, not an approximation. That is
only possible because a seed is available: part of the score is `Σ(desiredTime − goal.time)`, and
`desiredTime` comes from the seed's magic square. This is precisely the board-time offset that made
row scoring impossible for the bare row-permalink view — which is why that view still reports plain
summed length and says so.

`SynergyCalculator` is module-private inside `generator.js`, so it is ported in `board_synergy.js`,
including two quirks its numbers depend on: `unifyTypeSynergies` iterates *type* keys only (which is
the mechanism behind "a subtype only fires when another goal carries the matching type"), and
`filterRowtypeSynergies` **returns early** rather than continuing when a rowtype category has fewer
than five entries. `verify_board_synergy.js` proves the port two ways on every build — every
magic-square value against the generator's own `difficulty` / `desiredTime`, and every line of every
generated board against the `[minimumSynergy, maximumSynergy]` bounds the generator enforces
(25,300 squares and 12,144 lines at last run).

The line table sorts by length, synergy, or RBA risk, and each line breaks down into *goal overlap*
(shared categories), *row bonuses* (whole-row categories that only pay out with all five squares),
and *time vs board budget*. Selecting a line highlights it on the grid and narrows the index to
those five squares. Synergy is banded against the profile's own range rather than against zero —
the generator only emits lines inside `[-3, 7]` for normal, so a plain positive/negative verdict
would read "helps" twelve times and rank nothing.

## Row permalinks

The goal index accepts the same query shape as ootbingo's `bingo-popout.html`:

```
goals-page.html?title=COL1&goal=Milk&goal=Defeat+both+Flare+Dancers&goal=9+Hearts+%28no+duping%29
```

`title` once, `goal` repeated per square — built by `board.js`'s `openRowPopout` as
`new URLSearchParams([["title", title], ...goals.map(g => ["goal", g])])`. Paste a row popout link
straight from a board and the page will:

- list the squares **in board order**, with length and RBA markers, and narrow the index to them;
- switch board mode to match the row, since a board is generated in one mode and the squares would
  otherwise silently vanish behind the mode facet;
- **name the RBA clashes inside that row** — the reason the feature exists. Routing one square with
  RBA can invalidate another, and `conflicts.json` already knows which pairs;
- flag setup shared by three or more squares, so it gets done once;
- report any goal name that is not in the v10.6 list rather than dropping it.

Length is shown as the plain sum of the listed goal times and labelled *before synergy* — the
generator's real figure also folds in rowtype thresholds and the board's per-square time offsets,
which a bare list of goal names does not carry.

## The stream popout

`out/popout.html` is a vertical strip meant to sit beside a 4:3 Ocarina of Time capture inside a
16:9 canvas. At 1920x1080 the game fills 1440x1080, which leaves a 480px column — that is the shape
it is designed for, though every measurement is in viewport units, so resizing it works.

It takes either input shape:

```
popout.html?seed=523297&version=10.5.1&line=col1&timer=1
popout.html?title=ROW1&goal=Milk&goal=Defeat+both+Flare+Dancers&goal=…
```

The first generates the board locally from the embedded generator, so one URL survives a re-roll.
The second is ootbingo's own popout query, so a link copied off a board works with the host swapped.
The two can be combined: naming the squares **and** giving a seed shows the seed in the header
without regenerating anything. That is what the goal index does — see below.
Parameters may also be given after a `#` — an OBS "Local File" browser source drops the query
string, and a streamer would otherwise be looking at the help text with a URL that reads correctly.

| parameter | default | what it does |
| --- | --- | --- |
| `line` | `row1` | `row1`–`row5`, `col1`–`col5`, `tlbr`, `bltr` |
| `timer` | off | stopwatch: click or space to start and pause, right-click or `R` to reset |
| `chat` | `28` | percent of the height left empty at the bottom for a chat widget |
| `chathint` | off | draws that reserved band so it can be positioned, for setup only |
| `head` | on | `head=0` drops the title bar |
| `icons` | on | `icons=0` drops the item icons |
| `theme` | dark | `light` for a light scene |

### Opening it from the goal index

Load a board or paste a row on the goal index, select a line, and its detail card carries **Open
stream popout** and **Copy link**, with the pixel size shown next to them. Nothing pops up on its
own — a window appearing by itself mid-race is hostile, and OBS wants a URL far more often than a
second browser window. The window is opened at 4:9 scaled to fit the screen, rather than always
asking for 1080 tall and landing partly offscreen.

The squares are passed **by name**, not as `seed` + `line`. The two pages disagree about the order
of BL-TR: the index uses the generator's own `INDICES_PER_ROW` (`[4, 8, 12, 16, 20]`, top-right
first) while ootbingo's popout emits it bottom-left first. Naming the squares is the only way to
guarantee the strip shows exactly what is on screen, in the same order, without editing a port that
`verify_board_synergy.js` checks against the real library. The seed rides along purely as the header
label.

Clicking a square toggles it done; clicking an icon toggles it; clicking a counter increments it and
right-click decrements. A square is done or it is not — there is no third "blocked" state, so no
glyph is needed to tell two marked states apart. Marks and the clock are written to `localStorage`,
keyed by the squares themselves, because an OBS browser source reloads whenever the scene is
re-added and losing a running clock mid-race is worse than not having one.

The window title is the constant string **`OoT Bingo Popout`** for every line and every input shape.
OBS Window Capture matches on the title, so a title carrying the line name would stop matching the
moment a streamer switched lines and the source would go blank mid-race. `build_popout_page.js`
fails the build if that title is ever made dynamic again.

Four things differ from ootbingo's popout, all for legibility at stream distance and bitrate:

- **one type size for the whole column**, binary-searched so the longest goal still fits. Fitting
  each square separately wins a few points on the short ones but makes the column look ragged and
  implies the big goals matter more.
- **icons drawn at 3-4x with `image-rendering: pixelated`.** They are 32px pixel-art sprites, so
  nearest-neighbour is what they were drawn for.
- **the goal text is never hidden.** ootbingo's tracker can replace text with icons alone
  (`hideText`); a viewer cannot hover a stream to find out what the icons meant.
- **done changes the ground, the left bar and the text at once**, so it reads as a lightness and
  structure difference rather than a hue a colourblind viewer or a low-bitrate encoder could lose.

The icons and the regex rules that attach them come from ootbingo's `lib/item-tracker/`, imported
by `build_popout_data.js` rather than retyped — `trackerData.js` is order-sensitive, and a second
copy is a second thing to get wrong. The 82 `.ico` files carry frames up to 256x256 (`slot.ico`
alone is 115 KB), so the build pulls the 32x32 frame out of each and re-encodes it as a PNG data
URI: 524 KB of `.ico` becomes 114 KB. A rule naming an icon that does not exist fails the build,
since the alternative is an empty box on someone's stream.

## How strongly the pages claim things

An RBA write lands on a byte. Whether that helps or hurts usually depends on what you already had,
so the pages distinguish two cases rather than calling everything destruction:

| marker | meaning |
|---|---|
| `▲ RBA can complete it` | the write satisfies the goal outright |
| `◆ RBA shortcut` | the write makes the goal much cheaper |
| `✖ RBA can remove it for good` | the state lives in bit 1 or bits 5-7, which RBA can never be the first to set — only re-obtaining it in game restores it |
| `◈ RBA overwrites this` | the write touches the same state the goal measures, but the outcome depends on your before-state |

Odd Mushroom is the clarifying example: it assigns the heart-piece count to 1, which lowers a 3 but
raises a 0. That is an overwrite, not a wreck, and the effect table shows it with a neutral `=`
rather than a green `+` — because on an *assigning* byte "gained" is not a meaningful claim.
`build_rba_table.js` tags each write `flags` or `assign` for exactly this reason.

Permanence is asserted only where it is known. Recipes carry an explicit `destroysPermanently` list,
because a composite goal like *3 Shields* depends on the Hylian and Mirror Shield without naming
them, and no string match can infer that. Where a recipe does not say, the build falls back to
matching the goal name against the computed unwritable labels — i.e. it defaults to the weaker claim.

Current split across the 107 linked goals: **36** RBA can complete, **33** it shortcuts,
**32** it can remove for good, **17** it merely overwrites. (The buckets overlap — a goal can be
both completed and destroyed depending on the modifier.)

## Half-milk is not a sixth option

Writing 31 requires the **target** byte to already read 26 — and `ITEM_BOTTLE_MILK_FULL` *is* 26, so
this is not a numeric coincidence but the ordinary "drink a full bottle of milk, get half a bottle"
path, operating on whatever byte RBA has aimed the bottle at
(`Inventory_UpdateBottleItem`, `z_parameter.c:2080`, which tests the same address it writes).

The consequence took a failed in-game test to see. **RBA cannot write 26**, so a flags byte has to
*arrive* at 26 as (a writable value) OR (bits gained legitimately). Check which writable values have
no bits outside 26 and exactly one qualifies — **24** — and `26 − 24 = 2`, so the missing piece is
always **bit 1** of whichever byte is targeted:

| byte | bit 1 | can the game grant it back? |
|---|---|---|
| swords / shields | Master Sword | **yes** — `Sram_OpenSave` (`z_sram.c:578`) ORs the owned bit back on any adult load |
| tunics / boots | Goron Tunic | **yes** — buy it again |
| dungeon items | Compass | **yes**, if that dungeon's chest is still unopened |
| spiritual stones | Song of Storms | **no** — the Windmill Man teach sets `EVENTCHKINF_5B` (`z_en_fu.c:167`) and is checked first |
| songs | Requiem of Spirit | **no** — one-time Sheik teach |
| medallions | Fire Medallion | **no** — the blue warp is guarded by `EVENTCHKINF_49` |

So **half milk is possible on a flags byte if and only if bit 1 is re-grantable** — which is the
permanence rule arriving from the other direction, since bit 1 is exactly the bit RBA can never set.
That killed three `halfMilk: {ok: true}` claims (stones, songs, medallions) and rewrote a fourth; see
`validate_claims.js`, which now fails the build on either mistake.

Still unreachable for unrelated reasons:

- **Odd Mushroom (heart pieces)** — heart pieces add 16 at a time, so the low nibble can never land
  on `1010`. *(Derived here, not stated by ZSR, which only says "obtain a value of 26".)*
- **Pocket Egg / Pocket Cucco** — ZSR lists both as impossible.
- **Item slots** — pointless; full milk can only sit in a real bottle slot.
- **Dungeon items** — reachable but *dominated*: catching bugs (29) and opening the same chest
  reaches the identical Boss Key + Compass + Map one step sooner.

## Some goals have a spawn window

*Defeat a Skull Kid* is the one goal in v10.6 whose target can stop existing. `EnSkj_Init`
(`z_en_skj.c:422`) calls `Actor_Kill` on every fightable Skull Kid when
`INV_CONTENT(ITEM_TRADE_ADULT) < ITEM_POACHERS_SAW`.

That reads as a prerequisite and is not one. The slot defaults to `ITEM_NONE` = `0xFF` = 255, and
`255 < 50` is false, so the Skull Kids are there on a fresh file. What the check actually carves out
is a **dead window** across adult trade stops 1-5:

| adult trade slot | value | spawns |
|---|---|---|
| `ITEM_NONE` — quest not started | 255 | yes |
| Pocket Egg → Odd Potion | 45-49 | **no** |
| Poacher's Saw → Claim Check | 50-55 | yes |

So the goal is done *before* the adult trade quest starts, or *after* Poacher's Saw — and every
adult-trade RBA parked at stops 1-5, including the Odd Potion write that reaches the spiritual-stones
byte, sits inside the window. v10.6 already prices this: the goal carries `poachers 0.5`, which is
this spawn gate rather than the songs route it looks like.

The three exempt Skull Kids (the Saria's Song / mask trade one and the two ocarina-game ones) cannot
satisfy the goal anyway — their action funcs set `unk_2D3 = 0`, which suppresses
`CollisionCheck_SetAC`, so they have no damage collider at all. Every *killable* Skull Kid is behind
the gate.

Two side findings, both from the same actor: RBA can write the tested byte directly — Green Potion
(`0x16` = 22) on C-Right targets `SLOT_TRADE_ADULT`, and all six writable values are below 50 — and a
defeated Skull Kid drops a guaranteed 200-rupee (`ITEM00_RUPEE_ORANGE` → `ITEM_RUPEE_GOLD`), which
bingo does not price against any rupee goal.

## One dungeon, one C-Right item

The dungeon-item bytes share a layout but not an address, so a goal about a single dungeon now names
only its own item — *Map & Compass in Water Temple* shows **Fairy Bow + Ice Arrow, 0x39**, not the
whole trade quest. Multi-dungeon goals (*4 Maps*, *3 Boss Keys*) still list all seven, because they
genuinely span them.

## Accessibility

**No meaning is carried by colour alone.** The semantic core here is gain / loss / permanent, which
is the red-green axis — the most common colour vision deficiency. So every state also carries a
glyph and a word: `+` gained, `−` lost, `✖` can never be written back. Both pages stay fully
readable in greyscale. The colour half of that rule is machine-checked on every build; the glyph
half is a review discipline.

## Strategy notes

218 of the 269 goals carry per-goal strategy notes from **TKC's OoT Bingo goal-strategy post**,
via an English translation. 174 sections, 865 blocks, 375 links — **362 of them YouTube clips**.

The post is written for v10.5, so headings are matched to v10.6 three ways: exact name (152 of 174),
an `N` template expanded by regex (`N Songs` covers 3/4/6/7/8/9/10 Songs), and a short alias list for
goals v10.6 renamed. Every alias was settled by reading the section body rather than by string
similarity — *Defeat Shadow Link* is the Japanese name for Dark Link, and its section describes the
Water Temple room. `tkc_tips.js` fails the build if any heading matches nothing.

Sections are stored once and referenced by index. Many goals share one section, and inlining per goal
roughly quadrupled the payload (261 KB → 158 KB minified).

**Videos are click-to-load.** 362 embeds rendered eagerly would be absurd, and it also means the page
makes no third-party request until a reader asks for one. Each play button expands an inline
`youtube-nocookie` player with the timestamp preserved, plus a plain link out in case a strict CSP
blocks the frame.

Where the translation lost a link label the parser regenerates one from the URL, which leaves the
visible text reading "video". That is fine on screen — the sentence around it says what it is — but a
screen reader navigating by link would hear "video" seven times in one card, so each button borrows
the phrase that introduces it: *"Bombchu + Hover Boots — play video"*.

Every card is attributed to TKC with a link to the original and a note that it describes v10.5.

## Community data, and how it is trusted

Some things exist in neither input workspace. Silver rupees are per-scene `ovl_En_G_Switch` actors
and `E:/oot` has no extracted scene data, so that list was the project's largest gap for a long time.
It, and several others, now come from the bingo community — kept in `community_locations.js`, marked
`confidence: 'community'`, and never merged into the decomp-derived data.

What makes them trustworthy is that they are **checkable against evidence that had no hand in
producing them**. `validate_community.js` cross-references each list against bingo's own synergy
categories and goal counts, and against `collections.js`:

- **16 silver rupee rooms.** Their area set is exactly the set of area synergies the "Clear N Silver
  Rupee Rooms" goals carry, and `spirit` rises 2 → 3.5 → 5 → 6 → 7 as the goal grows 4 → 10.
- **6 gold rupee chests.** Five of six areas are corroborated by the goals' own `botw`, `storms`,
  `strength`, `gtg` and `fire` synergies.
- **10 bean patches**, nine with a gold skulltula. Those nine match `collections.js` area for area —
  and the tenth, Zora's River, is precisely why the goal is *All 9 Soft Soil Skulltulas* while the
  plant goals reach 7.
- **15 Stalfos** across 8 rooms, against a maximum goal of 10.

The same pass corrected two of my own recorded guesses: Dodongo's Cavern was listed as holding
silver rupees (it holds none), and "DMC Song of Time block" was listed among the gold rupee chests
(it is Fire Temple after the elevator). One reasoned guess survived — the note that `ganonchu`
pointed at a Bottom of the Well chest was right.

### On the page

Thirty goals carry it. The card is built from the same vocabulary as every other card — `.card.span`,
an uppercase `h3`, a `p.strongline`, a `.kv` grid — with one addition: a `.modnote` naming the
source. That footnote is a deliberate design decision rather than politeness. Every other fact on a
goal card is a proved byte offset or a value read straight out of the goal list; dropping racer
knowledge into the same layout without a marker would lend it the same authority.

The count line carries the shape a router actually wants — *"10 of 16 — 6 can be skipped"*, or
*"6 of 6 — the whole set, with nothing to spare"* — and the lead sentence is reserved for something
the count does not already say.

### Heart pieces are priced twice

The per-heart-piece timings come split by whether the run is doing the adult trade quest, which is
exactly the choice an adult-trade RBA forces: parking the sequence at a stop to write a byte puts you
in the trade-quest column. Committing to it **saves** 11s on the piece above Dodongo's Cavern and 9s
on the cow piece, **costs** 5s on lower crater, and removes four Lost Woods river routings that are
only priced without it. Thirty-three entries map onto a v10.6 goal; eleven use shorthand that is left
unmapped rather than guessed at.

If those paths move, edit the constants at the top of `parse_goals.js` and `build_rba_table.js`.

## The mechanic in one paragraph

`Inventory_UpdateBottleItem` writes `inventory.items[equips.cButtonSlots[button - 1]] = item`. With a
bottle on **B**, `button == 0`, so `cButtonSlots[-1]` reads `ItemEquips + 0x03` — which is
`buttonItems[3]`, the **item ID on C-Right**. That ID becomes a raw byte offset into `Inventory`
(NTSC 1.0 base `0x11A644`), and the new bottle content is written there. Only six values can ever be
written: `20` empty, `24` fairy, `25` fish, `28` blue fire, `29` bug, and `31` half-milk — the last
only when the target byte already reads `26`, because the milk substitution tests the *target*
address rather than what is on B.

The structural fact everything else hangs off: the adult trade items `ITEM_POCKET_EGG` (0x2D) through
`ITEM_CLAIM_CHECK` (0x37) are consecutive item IDs **and** consecutive `Inventory` bytes, and the
trade sequence advances through them in exactly that order. The trade sequence is therefore a one-way
cursor over the RBA target bytes — upgrades, then quest items, then dungeon items — and each byte is
writable during exactly one window of a run. That is where most of the traps come from.

- 269 goals, 21 archetypes.
- 107 goals have an RBA relationship: **36 completed**, **33 shortcut**, **32 removable for good**,
  **17 overwritten** (buckets overlap — a goal can be both, depending on the bottle value).
- 60 of 159 C-Right offsets are actually reachable.
- 100 gold skulltulas mapped; every bingo skulltula area/dungeon/child count reproduced exactly.
- 363 RBA-implied goal conflicts checked against bingo's own synergy numbers: 70 already priced,
  158 priced *positively*, 135 unpriced (21 of those from a route bingo does not model).
- Every write is reported as two outcomes — what it sets and what it clears — computed from the byte
  layout rather than written by hand. A write assigns the whole byte, so that is the entire
  transaction; whether a cleared bit can be re-obtained is a routing question left to the player.

## A note on `out/`

Generated files are committed so the data is readable without a Node run and without the two external
workspaces. If you would rather not track them, add `rba-data/out/` to `.gitignore` — `build_all.js`
regenerates everything.
